# 802.11 Frames — Management, Control, Data

## Learning Objectives
- Understand 802.11 frame format: Frame Control, Duration, Addresses, Seq Control, Frame Body, FCS
- Learn Management frames: Beacon, Probe Req/Resp, Auth, Assoc Req/Resp, Deauth, Disassoc, Action
- Learn Control frames: RTS, CTS, ACK, Block Ack
- Learn Data frames: Data, QoS Data, Null, EAPOL (4-way handshake)
- Understand Frame Control bits: Type/Subtype, To/From DS, Protected, Retry, Power Mgmt
- Map frame types to Wireshark filters and VAPT evidence

## Theory

### Frame Format

```
802.11 Frame (max 2346 bytes):
0-1: Frame Control (2 bytes)
2-3: Duration/ID (2 bytes)
4-9: Address1 (6 bytes) — RA (Receiver Address)
10-15: Address2 (6 bytes) — TA (Transmitter Address)
16-21: Address3 (6 bytes) — BSSID or SA/DA
22-23: Sequence Control (2 bytes) — Seq Num + Frag Num
24-29: Address4 (6 bytes, optional) — WDS when To DS=1 From DS=1
30-...: Frame Body (0-2304 bytes) — IE for management, LLC+IP for data
...-...: FCS (4 bytes) — CRC32

Frame Control (16 bits):
Bits 0-1: Protocol Version (0)
Bits 2-3: Type (0 Management, 1 Control, 2 Data, 3 Extension)
Bits 4-7: Subtype (Beacon 8, Probe Req 4, Probe Resp 5, Auth 11, Assoc Req 0, Assoc Resp 1, Deauth 12, Disassoc 10, Action 13, RTS 11, CTS 12, ACK 13, Data 0, QoS Data 8)
Bit 8: To DS (To Distribution System)
Bit 9: From DS (From DS)
Bit 10: More Frag (More fragments)
Bit 11: Retry (Retransmission)
Bit 12: Power Mgmt (Power save)
Bit 13: More Data (More data buffered for client in power save)
Bit 14: Protected Frame (Encrypted — WEP/WPA/WPA2/WPA3)
Bit 15: +HTC/Order (HT Control present / Order)

Addresses meaning depends on To/From DS:
To DS=0 From DS=0: Ad-hoc or management — Addr1 DA, Addr2 SA, Addr3 BSSID
To DS=0 From DS=1: From AP to client — Addr1 DA (client), Addr2 BSSID (AP), Addr3 SA (original source)
To DS=1 From DS=0: From client to AP — Addr1 BSSID (AP), Addr2 SA (client), Addr3 DA (dest)
To DS=1 From DS=1: WDS (AP to AP) — Addr1 RA, Addr2 TA, Addr3 DA, Addr4 SA
```

**Example:**
- Beacon: Type 0 Management Subtype 8, To DS=0 From DS=0, Addr1 FF:FF:FF:FF:FF:FF (broadcast), Addr2 BSSID (AP MAC), Addr3 BSSID, BSSID = AP MAC
- Probe Req: Type 0 Subtype 4, To DS=0 From DS=0, Addr1 FF:FF:FF:FF:FF:FF or specific BSSID, Addr2 Client MAC (SA), Addr3 FF:FF:FF:FF:FF:FF, SSID IE contains SSID client probes (PNL leak)
- Probe Resp: Type 0 Subtype 5, To DS=0 From DS=0, Addr1 Client MAC (DA), Addr2 BSSID, Addr3 BSSID, SSID IE contains real SSID (hidden SSID reveal)
- Auth: Type 0 Subtype 11, To DS=0 From DS=0, Addr1 BSSID or Client, Addr2 Client or BSSID, Addr3 BSSID, Auth algorithm (0 Open, 1 Shared WEP), Seq 1/2, Status 0 success
- Assoc Req: Type 0 Subtype 0, To DS=0 From DS=0, Addr1 BSSID, Addr2 Client MAC, Addr3 BSSID, SSID IE, RSN IE, HT/VHT/HE capabilities, Listen Interval
- Assoc Resp: Type 0 Subtype 1, To DS=0 From DS=0, Addr1 Client MAC, Addr2 BSSID, Addr3 BSSID, Status 0 success, AID (Association ID), RSN IE, HT/VHT/HE
- Deauth: Type 0 Subtype 12, To DS=0 From DS=0, Addr1 Client or BSSID or broadcast, Addr2 BSSID or Client, Addr3 BSSID, Reason code (1 unspecified, 4 disassoc due to inactivity, 7 class 3 frame from nonassoc STA, 8 disassoc STA leaving)
- Disassoc: Type 0 Subtype 10, similar, Reason code
- RTS: Type 1 Subtype 11, Addr1 RA, Addr2 TA, Duration
- CTS: Type 1 Subtype 12, Addr1 RA, Duration
- ACK: Type 1 Subtype 13, Addr1 RA, Duration
- Data: Type 2 Subtype 0, To/From DS as above, Frame Body LLC (DSAP 0xAA, SSAP 0xAA, Control 0x03, OUI 00:00:00, Type 0x0800 IP or 0x888E EAPOL), Protected bit indicates encrypted
- QoS Data: Type 2 Subtype 8, QoS Control field, TID, EOSP, Ack Policy, TXOP
- EAPOL: Data frame with LLC Type 0x888E, Frame Body EAPOL (Version, Type 3 Key, Key Info, Key Length, Replay Counter, Nonce, IV, RSC, ID, MIC, Key Data) — 4-way handshake M1-M4, PMKID in M1 key data

### Management Frames Deep Dive

**Beacon (Subtype 8):**
- Sent by AP every ~100ms (102.4ms default, beacon interval 100 TU, 1 TU = 1024 µs)
- Broadcast DA FF:FF:FF:FF:FF:FF, BSSID AP MAC, SA BSSID
- Frame Body: Timestamp (8 bytes, AP uptime), Beacon Interval (2 bytes, 100), Capabilities (2 bytes, ESS, Privacy, etc.), SSID IE (0, 0-32 bytes, empty for hidden), Supported Rates IE (1), DS Parameter Set IE (3, channel), TIM IE (5, Traffic Indication Map, DTIM), RSN IE (48, security), HT Capabilities IE (45), HT Operation IE (61), VHT Capabilities IE (191), VHT Operation IE (192), HE Capabilities IE (255 ext 35), HE Operation IE (255 ext 36), WPS IE (221 OUI 00:50:F2:04), Vendor Specific IEs
- **For PT:** Beacon is first recon — SSID, BSSID, channel, security, WPS, PMF, HT/VHT/HE, vendor, signal, beacon interval. Hidden SSID beacon has SSID IE length 0, but probe response reveals real SSID.

**Probe Request (Subtype 4):**
- Sent by client to discover APs — broadcast or directed
- Broadcast probe: SSID IE wildcard (length 0, SSID empty) — client asks "any AP?"
- Directed probe: SSID IE contains specific SSID — client probes for known SSID, e.g., `LAB-WIFI`, `Corp-WLAN`, `HomeWiFi` — PNL leakage, even when not connected
- DA FF:FF:FF:FF:FF:FF or specific BSSID, SA Client MAC, BSSID FF:FF:FF:FF:FF:FF or specific
- Frame Body: SSID IE, Supported Rates IE, HT/VHT/HE capabilities, Extended Supported Rates, etc.
- **For PT:** Probe requests leak PNL — client history, useful for targeted Evil Twin. Random MAC probing in modern OS (iOS, Android, Windows) uses random MAC for probe requests to reduce tracking, but still leaks PNL. Evidence: Client MAC, SSIDs probed, signal.

**Probe Response (Subtype 5):**
- Sent by AP in response to probe request — unicast to client
- DA Client MAC, SA BSSID, BSSID BSSID
- Frame Body: Similar to beacon — Timestamp, Beacon Interval, Capabilities, SSID IE (real SSID even if hidden beacon), Supported Rates, DS Parameter Set, RSN IE, HT/VHT/HE, WPS IE, etc.
- **For PT:** Hidden SSID reveal — hidden beacon has SSID length 0, but probe response contains real SSID. Filter `wlan.fc.type_subtype==5` and check SSID. Evidence: Frame number, BSSID, real SSID, channel, security.

**Authentication (Subtype 11):**
- Open System Authentication (most common, WPA2/WPA3) — 2 frames: Auth Req (client→AP, algorithm 0 Open, seq 1) and Auth Resp (AP→client, algorithm 0, seq 2, status 0 success)
- Shared Key Authentication (WEP, legacy, 4 frames: Req seq 1, Resp seq 2 challenge, Req seq 3 challenge response encrypted with WEP key, Resp seq 4 status) — insecure, WEP broken
- **For PT:** Auth is before assoc, usually open, not security relevant except for WEP shared key which is Critical (WEP). Evidence: Auth algorithm, seq, status, BSSID, client MAC.

**Association Request (Subtype 0):**
- Sent by client to AP after auth, to associate
- DA BSSID, SA Client MAC, BSSID BSSID
- Frame Body: Capabilities, Listen Interval (how often client wakes to check TIM), SSID IE (real SSID even if hidden), Supported Rates, RSN IE (client's requested security, AKM, ciphers), HT/VHT/HE capabilities, Extended Supported Rates, etc.
- **For PT:** Assoc Req contains real SSID even if hidden — another hidden SSID reveal method. RSN IE shows client's requested AKM (PSK, SAE, EAP) and ciphers. Evidence: SSID, BSSID, client MAC, RSN IE, HT/VHT/HE.

**Association Response (Subtype 1):**
- Sent by AP to client, status 0 success, AID (Association ID, 1-2007, client ID in BSS)
- DA Client MAC, SA BSSID, BSSID BSSID
- Frame Body: Capabilities, Status Code (0 success, 1 failure, etc.), AID, Supported Rates, RSN IE (AP's selected security), HT/VHT/HE, etc.
- **For PT:** Status code — 0 success, non-zero failure (e.g., 1 unspecified failure). AID. Evidence: Status, AID, BSSID, client MAC.

**Deauthentication (Subtype 12):**
- Sent by AP or client to deauthenticate — "disconnect"
- DA Client or BSSID or broadcast, SA BSSID or Client, BSSID BSSID
- Frame Body: Reason Code (1 unspecified, 4 disassoc due to inactivity, 5 AP unable to handle, 7 class 3 frame from nonassoc STA, 8 disassoc STA leaving)
- **Without PMF (802.11w):** Deauth is unauthenticated, not protected, attacker can spoof — `aireplay-ng --deauth` — DoS + handshake capture facilitation (force client to reconnect, capture handshake)
- **With PMF required (ieee80211w=2):** Deauth is protected, SA Query, attacker cannot spoof (except for unprotected deauth before association)
- **For PT:** Deauth flood detection — many deauth same BSSID short interval, reason 7, AP→client and client→AP, unauthenticated, DoS impact. Evidence: Frame numbers, BSSID, client MAC, reason codes, count, PMF status from beacon RSN capabilities MFPC/MFPR. Defense: PMF required.

**Disassociation (Subtype 10):**
- Similar to deauth, but disassoc — "disassociate but not deauthenticate" — less severe, but also unauthenticated without PMF
- Reason codes similar
- **For PT:** Similar to deauth, but subtype 10. Evidence: Frame numbers, reason codes, PMF status.

**Action (Subtype 13):**
- Various action frames — Block Ack, Radio Measurement, Spectrum Management, etc.
- For PT: Less relevant, but Action frames include SA Query for PMF.

### Control Frames

**RTS (Request to Send, Subtype 11):**
- Sent by client/AP to reserve medium — "I want to send, please reserve"
- RA Receiver, TA Transmitter, Duration
- For PT: RTS/CTS used for hidden node problem, not security relevant, but shows medium reservation

**CTS (Clear to Send, Subtype 12):**
- Response to RTS — "OK, medium reserved"
- RA Receiver, Duration
- For PT: Similar, not security relevant

**ACK (Acknowledgement, Subtype 13):**
- Ack for data frame — "I received"
- RA Receiver, Duration
- For PT: ACK, not security relevant, but shows successful reception

**Block Ack (Subtype 9):**
- Block acknowledgement for QoS — multiple frames acked together
- For PT: QoS, not security relevant

### Data Frames

**Data (Subtype 0):**
- LLC + IP + ... — actual data
- To DS=0 From DS=0: Ad-hoc, Addr1 DA, Addr2 SA, Addr3 BSSID
- To DS=0 From DS=1: From AP to client, Addr1 DA client, Addr2 BSSID AP, Addr3 SA original source
- To DS=1 From DS=0: From client to AP, Addr1 BSSID AP, Addr2 SA client, Addr3 DA dest
- To DS=1 From DS=1: WDS AP to AP, Addr1 RA, Addr2 TA, Addr3 DA, Addr4 SA
- Protected bit indicates encrypted (WEP/WPA/WPA2/WPA3)
- **For PT:** Data frames contain actual traffic — if open or WEP or WPA2 with known PTK, can decrypt and see IP, HTTP, etc. If WPA2/WPA3 with unknown PTK, data encrypted, can't decrypt without PTK. Evidence: BSSID, client MAC, encrypted or not, LLC type.

**QoS Data (Subtype 8):**
- QoS Control field — TID (Traffic ID, 0-7, QoS priority), EOSP (End of Service Period), Ack Policy, TXOP (Transmission Opportunity)
- For PT: QoS, not security relevant, but most data frames are QoS Data

**Null (Subtype 4) and QoS Null (Subtype 12):**
- Null data — no Frame Body, used for power save — client tells AP "I'm going to sleep" or "I'm awake, send buffered data"
- For PT: Power save, not security relevant, but shows client power management

**EAPOL (Data with LLC Type 0x888E):**
- EAPOL = Extensible Authentication Protocol over LAN — 4-way handshake for WPA2/WPA3, PMKID, EAP for Enterprise
- Frame Body: EAPOL Version (1 byte, 1 or 2), Type (1 byte, 0 EAP Packet, 1 EAPOL-Start, 2 EAPOL-Logoff, 3 EAPOL-Key, 4 EAPOL-Encapsulated-ASF-Alert), Length (2 bytes), Key Info (2 bytes, Key Type, Key Index, Install, Key ACK, Key MIC, Secure, Error, Request, Encrypted), Key Length (2 bytes), Replay Counter (8 bytes), Nonce (32 bytes, ANonce or SNonce), IV (16 bytes), RSC (8 bytes), ID (8 bytes), MIC (16 bytes), Key Data Length (2 bytes), Key Data (variable, RSN IE, GTK, PMKID)
- **M1:** AP→client, ANonce, Key ACK, no MIC, no key data (or PMKID in key data for PMKID)
- **M2:** Client→AP, SNonce, MIC, RSN IE, key data
- **M3:** AP→client, ANonce, MIC, Install, Key ACK, Key MIC, Secure, Encrypted, GTK, RSN IE, key data
- **M4:** Client→AP, MIC, Secure, no key data, ACK
- **For PT:** EAPOL is 4-way handshake — need SSID, BSSID, client MAC, ANonce, SNonce, MIC for offline audit (authorized only). PMKID in M1 key data — clientless, single frame, no deauth. EAP for Enterprise — PEAP, EAP-TLS, MSCHAPv2 challenge/response. Evidence: Frame numbers, BSSID, client MAC, ANonce, SNonce, MIC, PMKID hex, EAP type, identity.

## Attack → Defense → Retest

- **Attack:** Observe beacon, probe req PNL leak, hidden SSID via probe resp, deauth flood without PMF, handshake capture
- **Defense:** Hidden SSID not security (focus on WPA2/WPA3), random MAC probing (modern OS), disable auto-connect to open, PMF required ieee80211w=2, strong PSK, WPS disabled, WPA3-only
- **Retest:** Probe req uses random MAC and wildcard SSID (no PNL leak), hidden SSID still not security, beacon no WPS IE, PMF required deauth spoof fails, handshake audit fails with strong PSK
