## Theory

### 4-Way Handshake Purpose — Derive PTK, Install Keys, Verify PMK

**Purpose:**
- Derive PTK (Pairwise Transient Key) from PMK + ANonce + SNonce + BSSID + Client MAC via PRF — fresh PTK per association
- Verify both parties know PMK (via MIC with KCK) — authentication
- Distribute GTK (Group Temporal Key) for broadcast/multicast — encrypted with KEK, MIC with KCK
- Install PTK and GTK — start data encryption with TK CCMP
- Prevent replay via replay counter — increments

**PMK never sent over air — only derived — attacker who captures handshake can try offline PSK audit via PBKDF2 + PRF + MIC verification — only if PSK weak and authorized.**

**SNonce (Supplicant Nonce):**
- 32 bytes random from client — e.g., `d4e5f6...` 32 bytes — fresh — client generates after receiving ANonce — now client has ANonce + SNonce + PMK + BSSID + Client MAC → derives PTK via PRF-512

**PTK Derivation (WPA2):**
```
PTK = PRF-512(PMK, "Pairwise key expansion" | min(BSSID, Client MAC) | max(BSSID, Client MAC) | min(ANonce, SNonce) | max(ANonce, SNonce))

PRF-512 = HMAC-SHA1 based PRF, 512-bit output? Actually for CCMP, PTK 384-bit (48 bytes) — PRF-384? Let's check: For CCMP, PTK 384-bit = KCK 128 + KEK 128 + TK 128 = 384-bit. For TKIP, PTK 512-bit? Actually TKIP needs 2 TKs + MIC keys, so PTK 512-bit. But for CCMP, 384-bit.

Example:
PMK = PBKDF2("WiFiForgeLab123!", "LAB-WIFI", 4096, 32 bytes)
ANonce = a1b2c3... 32 bytes
SNonce = d4e5f6... 32 bytes
BSSID = AA:BB:CC:DD:EE:FF
Client MAC = 11:22:33:44:55:66
PTK = PRF(PMK, "Pairwise key expansion", min(AA:BB:CC:DD:EE:FF, 11:22:33:44:55:66), max(...), min(a1b2..., d4e5...), max(...)) — 48 bytes
KCK = PTK[0:16] 16 bytes
KEK = PTK[16:32] 16 bytes
TK = PTK[32:48] 16 bytes
```

**KCK (Key Confirmation Key):**
- 128-bit (16 bytes) — part of PTK — used for MIC — HMAC-SHA1(KCK, EAPOL frame) — MIC in M2, M3, M4 — proves sender knows PTK (which proves knows PMK, which proves knows PSK for PSK mode)

**MIC (Message Integrity Code):**
- HMAC-SHA1(KCK, EAPOL frame) — 16 bytes — in M2, M3, M4 — verifies EAPOL integrity and sender knows PTK
- For offline audit: Attacker tries PSK → PMK via PBKDF2 → PTK via PRF with captured ANonce, SNonce, BSSID, Client MAC → KCK → recompute MIC over captured EAPOL M2 frame → compare with captured MIC — if match, PSK correct — hashcat does this

**Replay Counter:**
- Same as M1 (1) — client uses same replay counter as M1 in M2 — AP checks replay counter, prevents replay

**Key Data:**
- RSN IE — client's RSN IE — same as AP's? Actually client's RSN IE in M2 — for verification

**For PT:** M2 has SNonce, MIC, replay 1, SA client DA BSSID — evidence SNonce, MIC, BSSID, client, etc.

### What is Needed for Offline Audit (Authorized Only) — PSK Mode

**For WPA2-PSK offline audit (authorized captures only, lab PCAPs, own lab, explicit ROE, not public):**
- **SSID:** For PBKDF2 salt — e.g., LAB-WIFI
- **BSSID:** AA:BB:CC:DD:EE:FF — for PTK derivation
- **Client MAC:** 11:22:33:44:55:66 — for PTK
- **ANonce:** From M1 — 32 bytes — e.g., a1b2c3...
- **SNonce:** From M2 — 32 bytes — e.g., d4e5f6...
- **MIC:** From M2 — 16 bytes — e.g., 1234... — for verification
- **EAPOL M2 frame:** Full EAPOL M2 frame for MIC computation — hashcat needs M2
- **Wordlist:** rockyou.txt, etc. — for trying passphrases

**Process:**
1. Try passphrase from wordlist — e.g., `password`, `WeakPass123`, `WiFiForgeLab123!`
2. Derive PMK via PBKDF2-HMAC-SHA1(passphrase, SSID, 4096, 32 bytes)
3. Derive PTK via PRF(PMK, "Pairwise key expansion", min(BSSID, Client MAC), max(...), min(ANonce, SNonce), max(...)) — 48 bytes for CCMP
4. KCK = PTK[0:16]
5. Recompute MIC = HMAC-SHA1(KCK, EAPOL M2 frame with MIC zeroed? Actually MIC field zeroed for computation)
6. Compare recomputed MIC with captured MIC — if match, passphrase correct — PSK found

**Tools:**
```bash
# Convert PCAP to hashcat 22000 format (WPA2 EAPOL + PMKID)
hcxpcapngtool -o capture.hc22000 capture.pcapng

# Audit with hashcat (authorized)
hashcat -m 22000 capture.hc22000 wordlist.txt --force

# Or aircrack-ng older
aircrack-ng -w wordlist.txt capture.cap

# tshark to extract handshake
tshark -r capture.pcapng -Y "eapol" -T fields -e frame.number -e wlan.bssid -e wlan.sa -e wlan.da -e eapol.keydes.nonce -e eapol.keydes.mic -e eapol.keydes.replay_counter
```

**Ethics:** Only use on lab PCAPs like `wpa2-handshake.pcapng` which we generated with known passphrase `WiFiForgeLab123!` — never audit public Wi-Fi, only own lab with explicit ROE.

**For PT:** Offline audit is for weak PSK detection — if PSK weak (in wordlist), High finding — recommend strong PSK 20+ random not in wordlists.

### PMKID — Alternative to Handshake — Clientless, Single Frame

**PMKID (Pairwise Master Key Identifier):**
- Formula: PMKID = HMAC-SHA1-128(PMK, "PMK Name" | BSSID | STA MAC) — first 128 bits (16 bytes) of HMAC-SHA1
- PMKID = HMAC-SHA1-128(PMK, "PMK Name" + BSSID + STA MAC) — "PMK Name" is string "PMK Name" (8 bytes ASCII), BSSID 6 bytes, STA MAC 6 bytes — total 20 bytes input to HMAC-SHA1, output 20 bytes, first 16 bytes PMKID
- Sent in RSN IE PMKID List or EAPOL M1 key data — even without full handshake — first EAPOL or RSN IE of association — clientless
- First discovered 2018 by Steube and Gristina via `hcxdumptool` — clientless PMKID capture — no need for client, no deauth, single frame

**How PMKID is captured:**
- AP includes PMKID in EAPOL M1 key data if it has PMKID cache for fast roaming 802.11r or for client that previously connected — PMKID cache — AP caches PMKID for fast roaming
- Attacker can capture PMKID via `hcxdumptool` which acts as client, sends association request to AP, AP responds with M1 containing PMKID — clientless in sense no need for full handshake, just M1 — single frame — no deauth needed — less intrusive than handshake capture which needs client and possibly deauth if PMF not required
- `hcxdumptool -i wlan0mon -o capture.pcapng --enable_status=1` — captures PMKID

**Advantage over handshake:**
- Clientless — no need for client to be present — AP sends M1 with PMKID even if no client? Actually need to associate, but `hcxdumptool` associates as client, gets M1 with PMKID — still clientless in sense no need for legitimate client, no need to wait for client, no deauth
- Single frame — M1 with PMKID — vs handshake needs 4 frames M1-M4 or at least M1+M2
- No deauth — no DoS, less detection, more stealth — handshake capture often uses deauth if PMF not required to force client re-handshake — deauth is active, detectable, DoS — PMKID no deauth, less intrusive
- But still requires weak PSK to crack — PMKID offline audit same as handshake — PBKDF2 + HMAC-SHA1-128 — if PSK weak, crackable

**For PT:** PMKID is preferred over handshake if available — clientless, single frame, no deauth, less detection — but not all APs include PMKID in M1 — many do, especially with PMKID cache enabled for fast roaming — if PMKID not present, fallback to handshake capture (with deauth if authorized and PMF not required and lab).

**Example pmkid.pcapng:**
- f1 Beacon LAB-WIFI BSSID AA:BB:CC:DD:EE:FF Ch6 WPA2-PSK CCMP PSK
- f2 EAPOL M1 SA BSSID DA Client? Or broadcast? Actually PMKID M1 SA BSSID DA client MAC or broadcast? In pmkid.pcapng, M1 with PMKID in key data — SA BSSID DA client or FF:FF:FF:FF:FF:FF? Usually DA client if client assoc, but PMKID can be captured even with client not fully associated? Let's assume SA BSSID DA client, key data contains PMKID

**For PT:** PMKID is High value — clientless, no deauth, single frame, less detection, but requires AP to include PMKID in M1 — not all APs do, but many do.

### Defense — Strong PSK, PMF, WPA3

- **Strong passphrase:** 20+ chars random not in wordlists, not SSID-related, unique per SSID, rotated, stored securely — `pwgen -s 20 1`, `openssl rand -base64 15`, Python secrets
- **PMF required ieee80211w=2:** Prevents deauth for handshake capture — WPA3 mandates required, WPA2 should have required — check beacon RSN Capabilities MFPC=1 MFPR=1
- **WPA3 where possible SAE:** SAE resists offline audit — forward secrecy — even if handshake captured, offline audit not possible without active attack? Actually SAE has forward secrecy, resists offline dictionary — better than PSK
- **No WPS:** wps_state=0 — WPS IE 00:50:F2:04 High 11k PIN flaw
- **Monitor for deauth floods:** WIDS detection — many deauth same BSSID short interval — alert
- **PMKID cache:** If not needed for fast roaming, disable PMKID cache? Actually PMKID cache is for fast roaming, but if PMKID present, risk — but PMKID requires weak PSK to crack, so strong PSK mitigates — strong PSK is defense
