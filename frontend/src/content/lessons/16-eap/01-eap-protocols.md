## Theory

### EAP (Extensible Authentication Protocol) — Framework for Authentication Not Method Itself Used in 802.1X

**EAP is framework for authentication not method itself used in 802.1X — EAP types: EAP-TLS mutual cert auth client cert + server cert most secure requires PKI, PEAP Protected EAP outer TLS tunnel with server cert inner auth MSCHAPv2 GTC widely used vulnerable if cert validation disabled, EAP-TTLS Tunneled TLS similar to PEAP inner PAP CHAP MSCHAPv2 etc, EAP-FAST Cisco PAC less common now, EAP-PWD Password WPA3 uses similar to SAE not common for Enterprise**

**EAP Types Detailed:**

- **EAP-TLS (RFC 5216):** Mutual cert auth client cert + server cert most secure requires PKI — client cert + server cert — mutual authentication — client validates server cert via ca_cert + subject_match, server validates client cert via CA checks revocation CRL OCSP correct EKU — no password — cert-based — resists rogue RADIUS if both validate — requires PKI client cert provisioning auto-enrollment via MDM/GPO SCEP EST — more complex but secure — for PT, EAP-TLS mutual cert most secure — if configured correctly — check ca_cert client_cert private_key subject_match — if missing, High? Actually EAP-TLS mutual cert most secure but if misconfigured still risk — recommend proper PKI client cert provisioning via MDM/GPO strong private key password ca_cert subject_match revocation checking
- **PEAP (Protected EAP):** Outer TLS tunnel with server cert inner auth MSCHAPv2 GTC widely used vulnerable if cert validation disabled — PEAPv0/EAP-MSCHAPv2 most common — outer TLS tunnel with server cert — inner auth MSCHAPv2 challenge/response — client validates server cert via ca_cert + subject_match — if no ca_cert, client accepts any cert rogue RADIUS risk — attacker rogue AP + rogue RADIUS presents self-signed cert client without ca_cert accepts sends MSCHAPv2 response to attacker captures challenge/response offline crack hashcat -m 5500 or asleap — even with strong password if MSCHAPv2 weak NTLM hash crackable — for PT, PEAP without ca_cert High — credential capture — recommend ca_cert + subject_match via MDM/GPO prefer EAP-TLS
- **EAP-TTLS (Tunneled TLS):** Similar to PEAP but inner can be PAP CHAP MSCHAPv2 etc — TTLS outer TLS tunnel with server cert inner PAP cleartext inside TLS but TLS protects still need cert validation if PAP and no cert validation password sent to rogue RADIUS worse than MSCHAPv2 challenge/response PAP is cleartext inside TLS but if TLS terminated by attacker cleartext captured — for PT, EAP-TTLS similar to PEAP — check cert validation — if no ca_cert, High — PAP cleartext inside TLS but if TLS terminated by attacker cleartext captured — worse than MSCHAPv2 — recommend ca_cert + subject_match
- **EAP-FAST (Flexible Authentication via Secure Tunneling):** Cisco PAC Protected Access Credential less common now — uses PAC provisioning — for PT, EAP-FAST less common — but check if used — PAC provisioning — for PT, EAP-FAST similar to PEAP — check cert validation
- **EAP-PWD (Password):** Password WPA3 uses similar to SAE Dragonfly not common for Enterprise — for PT, EAP-PWD not common — but WPA3 SAE uses similar zero-knowledge — for PT, EAP-PWD not common for Enterprise

**For PT:** EAP framework — EAP-TLS mutual cert most secure requires PKI, PEAP outer TLS inner MSCHAPv2 widely used vulnerable if cert validation disabled, EAP-TTLS similar to PEAP inner PAP CHAP MSCHAPv2, EAP-FAST Cisco PAC less common, EAP-PWD not common — for PT, check EAP method — PEAP without ca_cert High — EAP-TLS mutual cert most secure — EAP-TTLS similar to PEAP — check cert validation

### Certificate Validation — Critical — Detailed

**Client Must Validate Server Cert:**

- **ca_cert Pointing to Trusted CA:** ca_cert pointing to trusted CA — e.g., corporate CA cert /etc/certs/ca.pem — validates server cert chain to trusted CA — if rogue RADIUS self-signed cert not signed by corporate CA, validation fails — client rejects rogue RADIUS — secure — if no ca_cert, client accepts any cert — rogue RADIUS self-signed cert accepted — client sends MSCHAPv2 to attacker — credential capture High — for PT, check wpa_supplicant.conf ca_cert — if missing, High — PEAP without cert validation allows rogue RADIUS captures MSCHAPv2 for offline crack
- **subject_match or altsubject_match or domain_suffix_match to Ensure Cert is for Expected Server radius.corp.com Not Any Cert Signed by Same CA:** subject_match or altsubject_match or domain_suffix_match to ensure cert is for expected server radius.corp.com not any cert signed by same CA — e.g., subject_match=CN=radius.corp.com — validates server cert subject CN matches expected — altsubject_match=DNS:radius.corp.com — validates alt subject DNS — domain_suffix_match=corp.com — validates domain suffix — without this, any cert from same CA accepted — e.g., if corporate CA signs cert for attacker.com, client with ca_cert but without subject_match would accept attacker.com cert signed by same CA — still rogue? Actually if CA is corporate CA and signs cert for attacker.com? But corporate CA should only sign certs for corp.com — but if compromised? For PT, subject_match ensures cert is for expected server radius.corp.com not any cert signed by same CA — good — recommend subject_match
- **Without This Any Cert from Same CA or Any Cert if No ca_cert Accepted → Rogue RADIUS:** Without ca_cert, any cert accepted — rogue RADIUS self-signed cert accepted — client sends MSCHAPv2 to attacker — credential capture High — with ca_cert but without subject_match, any cert signed by same CA accepted — e.g., if corporate CA signs cert for attacker.com? But corporate CA should only sign corp.com — but still recommend subject_match — for PT, without ca_cert, any cert accepted → rogue RADIUS — High — with ca_cert but without subject_match, any cert signed by same CA accepted — still risk — recommend subject_match

**Server Must Validate Client Cert for EAP-TLS Check Client Cert Signed by Trusted CA Not Revoked Correct EKU:**

- **Server Must Validate Client Cert for EAP-TLS:** For EAP-TLS mutual cert, server must validate client cert signed by trusted CA not revoked correct EKU Extended Key Usage — e.g., client cert EKU clientAuth — server checks client cert signed by trusted CA, not revoked via CRL OCSP, correct EKU clientAuth — if not, client cert invalid — for PT, check EAP-TLS server validation — if no revocation checking, Medium? - **For PT:** Certificate validation critical — client must validate server cert via ca_cert + subject_match, server must validate client cert for EAP-TLS via CA revocation EKU — without validation, rogue RADIUS — High
