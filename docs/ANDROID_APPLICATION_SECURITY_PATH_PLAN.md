# Android Application Security — path blueprint

**Status:** All 12 modules authored (25 lessons, 12 quizzes, nine source-case self-review labs). A01–A03 remain Preview; A04–A12 are Full source-first practice. No prebuilt APK or measured/graded dynamic lab is shipped. A source project now exists under `android-labs/notes-boundary/`, but was not compiled or executed in this workspace (no Android SDK/Java/Gradle/emulator; official SDK download endpoint unreachable). **Audience:** a learner aiming to assess an authorized Android APK and its on-device behaviour, not just replay API requests. **Decision:** one coherent path, two stages (**Foundations** and **Advanced / Full**), not two independent paths. The existing `android-pentesting` ID serves the Foundations and Full source-first path. Completing it must not claim dynamic proficiency without independently executed device labs. The existing Preview/Full experience is a product distinction, not a security boundary or verified grade.

## Graduate outcome and boundaries

Given an authorized APK/AAB or a reproducible test build, its version/signature, a test account, an emulator or owned test device, and scope rules, the learner should be able to: set up and troubleshoot an Android test environment; form a component/data-flow threat model; inspect manifest, resources, DEX/Kotlin/Java and native code where applicable; trace sensitive data to local and inter-app sinks; safely exercise exported components, deep links, providers, WebView, local persistence and runtime state; reason about TLS trust/pinning and anti-tamper without stopping at bypass; distinguish an app-side weakness from a backend/API weakness; verify impact on a controlled build; and identify limitations and remediation. Interview readiness means explaining **why** a control fails, Android version/target-SDK context, how to reproduce it, and which evidence would disprove the hypothesis. It does not follow automatically from self-marked XP or MCQs.

Not the primary scope: general web/API exploitation, iOS, malware development, attacks on third-party apps, credential theft or defeating protections on unowned apps. Use a brief hand-off into the separately planned API path for backend authorization, session, BOLA and server business logic; still teach mobile-specific client credentials, network configuration, WebView bridges and on-device traffic. Frida/pinning bypass is a *diagnostic technique on a permitted test target*, never the course's endpoint or proof of a vulnerability. No formal reporting course: keep concise evidence/next-test records as part of every lab.

## Instruction pattern per module

1. **Mechanism:** small Kotlin/manifest sample and Android API/target-version matrix; identify caller, callee and trust boundary.
2. **Worked trace:** one exact hash/build, source line or decompiled class, command and expected output; show both what it establishes and what it does not.
3. **Independent task:** new variant, no answer on the task screen; learner predicts an observable effect, executes only against a supplied/owned build, and records negative control.
4. **Feedback:** test oracle or precise model answer explains alternative hypotheses and secure implementation; reviewer may reject unsupported impact.
5. **Transfer:** same issue in a different Android version or cross-platform wrapper; learner chooses next safe test without a tool recipe.

Each advanced module now has an offline static exercise with three independent prompts. Dynamic tasks explicitly require Android runtime; **do not** count source reading as having performed dynamic testing. Most important milestones (A04, A05, A06, A08, A09, A12) require distinct built and exercised vulnerable-and-fixed demos before the path claims practical dynamic coverage. A sandboxed in-browser VM/device would be a major separate infrastructure project, not implied by the existing static site.

## Artifact contract before a module becomes available

- Source-owned, license-reviewed training app(s): Kotlin source, build recipe, pinned SDK/tool requirements, reproducible APK(s) and SHA-256, debug/release variants, vulnerable/fixed toggles, no real keys/accounts, self-contained test data. APK binaries only if license, size and hosting policy permit; otherwise verified build instructions with hashes for official downloads. Avoid distributing third-party APKs without permission.
- Fixture set per lab: manifests/resources/JADX excerpts where licensing allows, anonymized logcat and proxy traces, provider/deep-link test inputs, expected outputs, Android API/target matrix, cleanup/reset instructions and artifact hashes. Pin exact demo/version/API levels; never claim a finding generalizes to every Android release.
- Lab contract: `prerequisites`, `scope`, `setup`, `artifact IDs`, `hypothesis`, `actions`, `observations`, `negative control`, `evaluation`, `remediation`, `retest`, `limitations`, and MASVS control / MASWE / MASTG test reference *when a stable applicable mapping has been checked*. Not every teaching activity is itself an OWASP conformance test.
- Feedback: machine-checkable answers only where the grader can actually validate a source hash, build/version and result; local quiz completion is self-review. Never label untrusted local imports, runtime screenshots or self-attested device results as verified professional competence.
- Assessment: per-module diagnostic quiz plus at least one worked and one independent investigation; A12 includes a fresh app variant, resettable tasks, alternative explanation, and reviewer rubric. Interviews: short verbal prompts on architecture, evidence, false positives, dynamic-vs-static disagreement and platform-version differences.

Storage A06/A12; Crypto A06/A10; Auth A05/A07/A10; Network A07; Platform A01/A04/A05/A08; Code A03/A11; Resilience A09/A10/A11; Privacy A06/A08. Map **individual** exercises to appropriate MASWE weaknesses and MASTG v2 atomic tests as they are authored, rather than claiming all controls are covered by topic names. OWASP distinguishes MASVS control groups, MASWE weaknesses and MASTG tests; MASTG v2 specifically separates steps, observations and evaluation. Android's own checklist covers storage, providers, IPC, networking, WebView, dynamically loaded code and native code. The repo now has an available **source-first** Android card in `frontend/src/content/learning-paths.json`. Nine additional advanced modules have original case excerpts and self-review labs, but all device outcomes remain untested. `modules.json`, `quizData.ts`, `labs.ts`, `scenarios.json`, `challenges.json` and local progress currently use mostly wireless-specific examples. `ModuleDetail.tsx` has PCAP/Wi-Fi-specific lab panels; Android labs require their own generic artifact view or Android-specific lab UI rather than pretending an APK is a PCAP. `module-ordinal.ts` uses path-local numbering for the released Foundations modules. `contentAccess.ts` derives Preview from phase ≤2, so assign A01–A03 phase 1–2 and verify tier counts per path; do not silently change wireless's six-module preview. **Release status, not a promise of field proficiency:** A01–A12 have authored reading, short checks and nine interactive source-case self-reviews. Only the Notes Boundary source project can be built into an app; it covers the mock note/URI boundary, not the independent storage, WebView, TLS, crypto or native/code-loading snippets. No APK or device observation has been produced in this sandbox. `.github/workflows/android-demo.yml` offers an **unexecuted**, manually triggered GitHub-hosted debug build for the two demo variants; on success, artifacts are downloadable from Actions for 14 days, not published to the course site. The user must hash and test on an owned emulator. Follow-up work before claiming dynamic course completion: execute the build workflow; install/test both variants with a pinned OS/target matrix; ship separate *built* apps or licensed authorized lab fixtures for A06–A11; add independent reviewer feedback and a genuine retest exercise. The Full tier denotes product experience, not protected content or verified competency. Browser-local quiz/self-review progress cannot stand in for a completed Android pentest.

## Benchmark honestly

HTB Academy advertises guided courses, practical interactive labs, an in-browser pentesting VM and assessed certification paths; those are **capabilities to compare**, not claims SecCraft already has. PortSwigger's Academy is excellent for web/API mechanics but should be a *handoff*, not a substitute for Android IPC/storage/runtime practice. Comparable Android quality requires reproducible runnable apps, graded observations, maintained version matrices, realistic independent transfer tasks, accessible feedback and expert review—not more markdown or a bigger module count. Do not claim parity or job readiness until these exist. [HTB Academy](https://academy.hackthebox.com/) · [OWASP MASTG](https://mas.owasp.org/MASTG/).
