# SecCraft page-by-page source audit

Source inspection, 30 September 2026. This is **not** a rendered viewport, contrast, keyboard-navigation, screen-reader or browser visual sign-off. An available browser executable is still needed for those checks. Priorities describe the next possible frontend-only improvements, not claims that the work below is already done. Routes, identity, content and server-side access rules remain unchanged.

## First page completed: owner console (`/admin`)

- **Observed:** The previous page combined policy, accounts and audit in dense panels; a filter refetched *all* data and could overwrite an unsaved policy edit. Failed or slow account requests could leave rows from the prior filter visible. The unfiltered request silently used the API's default 100-row cap, and the audit displayed only 50 events without stating that bound. Approval was immediate, while rejection and suspension required confirmation. On small screens the row actions and long identifiers competed for width.
- **Changed:** The console now has separate capacity, policy, account and recent-activity sections; a compact header; grouped server-status filters; a responsive account table; visible loading, error, empty and bounded-list states; a change summary for audit entries; unsaved-change indication; a refresh-discard confirmation; and confirmation for approval/reactivation as well as rejection/suspension. Account-filter requests are independent of policy drafts, use the existing 200-row maximum, and clear previous rows before loading. Approval controls explain unavailable capacity, while the server still makes the decision. The first 200 results are explicitly **not** described as a total or as pageable. No API, backend, auth or owner authorization was changed.
- **Checked in source/tests:** The dedicated owner-console test covers draft retention across filters and status refresh, confirmation before approval, save payload and stale-row prevention after a failed request. Account-state tests still cover the owner versus non-owner rendering guard. The frontend checks do not establish the appearance of a real authenticated owner session.
- **Known limit:** The current owner API does not expose pagination or a total count. If a status contains more than 200 accounts, later accounts cannot be reached through this UI without a separate backend/API design and corresponding authorization tests.
